03

Concepts explained

Plain definitions, the formula where there is one, and a worked example from the projects.

Confusion matrix

Metric

A 2×2 table counting every prediction by what the model said and what was true: true positives (TP), false positives (FP), false negatives (FN) and true negatives (TN). Almost every classification metric is built from these four numbers.

From the e-commerce modelOf 23,466 held-out rows: TP 16,545 · FP 2,569 · FN 1,165 · TN 3,187. The model wrongly called 2,569 unhappy customers "satisfied".

Always check which class is "positive". Swapping it changes precision and recall completely.

Accuracy

Metric

The share of all predictions that were correct.

accuracy = (TP + TN) / (TP + FP + FN + TN)

Worked exampleE-commerce: (16,545 + 3,187) / 23,466 = 84.1%. But predicting "satisfied" for everyone already scores 75.5%, so the real gain is about 9 points.

On imbalanced data a useless model can look accurate. Always compare against the majority-class baseline.

Precision

Metric

Of everything the model flagged as positive, how much really was. It answers: "When the model says yes, can I trust it?"

precision = TP / (TP + FP)

Worked exampleTitanic: 625 / (625 + 211) = 0.748. About 3 in 4 passengers predicted "transported" actually were.

Precision can be pushed high simply by predicting "yes" rarely — check recall alongside it.

Recall (sensitivity)

Metric

Of all the real positives, how many the model found. It answers: "How much do I miss?"

recall = TP / (TP + FN)

Worked exampleE-commerce, dissatisfied class: 3,187 / (3,187 + 2,569) = 0.554. The model catches just over half of unhappy customers.

Recall of 1.0 is trivial — predict positive for everyone. It only means something next to precision.

F1 score

Metric

The harmonic mean of precision and recall — a single number that is only high when both are high.

F1 = 2 · precision · recall / (precision + recall)

Worked exampleE-commerce, dissatisfied class: 2 · 0.732 · 0.554 / (0.732 + 0.554) = 0.631. The threshold 0.666 was picked because it maximised exactly this number.

F1 ignores true negatives, so it suits "find the rare class" problems better than balanced ones.

Decision threshold

Metric

Models output a probability; the threshold is the cut-off that turns it into yes/no. 0.5 is only a default — lowering it catches more positives, raising it makes each "yes" more reliable.

From both projectsTitanic: moving from 0.50 to 0.42 raised accuracy from 77.84% to 78.18%. E-commerce: 0.666 balances catching unhappy customers against false alarms. Try it in the threshold lab.

Choosing the threshold on the test set makes the reported score slightly optimistic.

ROC curve

Metric

Plots the true positive rate (recall) against the false positive rate for every possible threshold. A perfect model hugs the top-left corner; random guessing follows the diagonal.

TPR = TP / (TP + FN)  ·  FPR = FP / (FP + TN)

Reading itEach point is one threshold. The curve shows every trade-off available; choosing a threshold just picks one point on it.

With very imbalanced data the ROC curve can look good while precision is poor — also check the precision–recall curve.

ROC-AUC

Metric

The area under the ROC curve, from 0.5 (random) to 1.0 (perfect). Intuitively: pick one random positive and one random negative — AUC is the probability the model gives the positive a higher score.

Worked exampleTitanic AUC 0.8687: take a transported and a non-transported passenger at random, and the model ranks the transported one higher about 87 times in 100. It does not depend on any threshold.

AUC measures ranking, not calibrated probabilities — a model can rank well and still be overconfident.

Precision–recall curve & average precision

Metric

Plots precision against recall across thresholds. Average precision (AP) summarises the curve in one number. A random model's precision equals the positive rate, so that is the baseline.

Worked exampleE-commerce AP is 0.904, but the baseline is already 0.755 (share of satisfied rows). The honest improvement is the gap between the two.

Unlike ROC-AUC, AP's baseline changes with class balance, so AP values are not comparable across datasets.

Log loss

Metric

Measures how good the predicted probabilities are, heavily punishing confident mistakes. Lower is better; 0 is perfect.

log loss = −mean( y·ln p + (1−y)·ln(1−p) )

Worked exampleE-commerce model: 0.404. Always predicting the base rate (0.755) would score about 0.557, so the model's probabilities carry real information.

A single wildly confident wrong prediction can dominate the average.

Brier score

Metric

The mean squared difference between predicted probability and the actual 0/1 outcome. Lower is better; gentler on confident mistakes than log loss.

Brier = mean( (p − y)² )

Worked exampleE-commerce: 0.122, against 0.185 for a constant 0.755 guess.

Also depends on class balance — compare to the constant-prediction baseline, not to zero.

Calibration

Metric

Whether predicted probabilities match reality: of all orders scored 0.8, about 80% should truly be satisfied. A reliability diagram plots predicted against observed frequency.

Why it matters hereA threshold like 0.666 only means something if 0.666 behaves like a probability. Both reports include reliability diagrams to check this.

Class weighting and heavy resampling often break calibration even when AUC holds.

Train / test split & stratification

Validation

The model learns on one part of the data and is scored on another it never saw. Stratifying keeps the class ratio the same in both parts.

From both projectsBoth use an 80/20 split with stratify=y and random_state=42. E-commerce: 93,863 train / 23,466 test. Titanic: 5,812 / 1,453.

A single split has variance: dropping just 15 rows before splitting moved the e-commerce AUC from 0.8057 to 0.7936.

Data leakage

Validation

When information unavailable at prediction time — or from the test set — slips into training. Scores look better than the model will really perform.

From the e-commerce projectSeller average delay was first computed on all rows, so test orders influenced their own features (AUC 0.7712). Computing it on training rows only gave 0.7698 — lower, but honest. Review text was also excluded, since it is written after the outcome.

Leakage rarely causes an error — it silently inflates results.

Cross-validation (k-fold)

Validation

Split training data into k parts; train on k−1 and score on the remaining one, rotating k times. The average gives a steadier estimate than one split.

From the Titanic projectRandomizedSearchCV used 5-fold CV: 30 candidates × 5 folds = 150 fits. The best CV accuracy was 80.49%, but on the untouched validation split it was 77.84%.

The CV score of the chosen configuration is optimistic, because it was chosen for being highest.

Selection bias (optimism)

Validation

Try many options and keep the best score, and part of that score is luck. The more options compared on the same data, the more optimistic the winner's number.

From both projectsTitanic: best CV 80.49% vs 77.84% on holdout. E-commerce: Optuna scored 30 trials on the same test set it reports 0.8057 on.

The fix is a separate tuning set or nested cross-validation, keeping the final test set untouched.

Class imbalance

Validation

When one class is far more common than the other. Models drift toward predicting the majority class, and accuracy becomes misleading.

From the e-commerce project75.5% of rows are satisfied. Class weighting (scale_pos_weight) raised dissatisfied recall from 0.38 to 0.59 but lowered AUC, so the final model instead tunes the threshold.

Resampling or reweighting changes probabilities — recheck calibration afterwards.

Hyperparameter search

Validation

Hyperparameters are settings chosen before training (tree depth, learning rate…). Grid search tries every combination; random search samples some; Bayesian search (Optuna) uses past trials to pick promising next ones.

From both projectsTitanic: grid of 162 combos for gradient boosting; random 30 of 26,244 for LightGBM. E-commerce: Optuna, 30 trials over 9 parameters.

More search means more optimism in the best score (see selection bias).

Decision tree & random forest

Model

A decision tree asks a sequence of yes/no questions about features. A random forest trains many trees on random samples of rows and features and averages them, which reduces overfitting.

From the Titanic projectSingle tree 73.37% accuracy; random forest 77.29%. Averaging many noisy trees gained about 4 points.

A single deep tree memorises training data — its test score is usually the weakest.

Gradient boosting & LightGBM

Model

Boosting builds trees one after another, each correcting the errors of the ones before. LightGBM is a fast implementation that grows trees leaf-wise and handles categorical features and missing values natively.

From both projectsBoth final models are LightGBM. The e-commerce model uses 694 trees with up to 127 leaves; the Titanic model settled on just 100 trees with 31 leaves.

Boosting overfits if trees are too deep or too many — tune with validation, not training scores.

Voting ensemble

Model

Combine several models: hard voting takes the majority label, soft voting averages probabilities, and weights let stronger models count more.

From the Titanic projectFour voting schemes over tree, forest, boosting and XGBoost scored 77.29–77.77% — none beat gradient boosting alone (78.05%), because the members made the same mistakes.

Ensembles help only when members disagree on different rows.

Feature importance (gain)

Model

How much each feature improved the model's splits, summed across all trees. "Gain" weights by improvement; "split" just counts uses.

From both projectsE-commerce: delivery_delay_days 15.9% of gain, delay_severity 8.3%. Titanic: CryoSleep_True 33.8%.

Importance shows what the model uses, not what causes the outcome. Correlated features also share credit unpredictably.

One-hot vs native categoricals

Data

One-hot encoding turns a category into 0/1 columns, one per value. LightGBM can instead split on categories directly without expanding them.

From both projectsTitanic one-hot encoded 4 columns (dropping the first level) to reach 16 features. E-commerce kept 5 categoricals native — product_category_name alone has 70+ values.

Categories in the test set that were never seen in training need a plan.

Missing values

Data

Options: drop the rows, fill with a statistic (median), add an explicit "Unknown" category, or predict the value with a model.

From the Titanic projectPredicting missing categoricals was only 72.3% accurate, so "Unknown" was used instead. Dropping remaining gaps cost 1,428 training rows (16.4%).

Dropping rows quietly shrinks and can bias the data — count what you lose.

ONNX

Deployment

Open Neural Network Exchange — a portable model format. A model trained in Python can run in C++, Java, or a web browser through ONNX Runtime, with no Python needed.

From both projectsBoth models are exported with onnxmltools. The Titanic model runs live in the browser via ONNX Runtime Web; the e-commerce export removes the ZipMap node so outputs are a plain probability array.

ONNX takes raw numbers in a fixed order — preprocessing and column order must match training exactly.

Questions about the portfolio as a whole

Project-specific questions live in each briefing.

Why are both final models gradient-boosted trees?Approach
Both datasets are tabular with mixed numeric and categorical columns — the setting where boosted trees are consistently strong.

Trees need no feature scaling, handle non-linear effects and interactions automatically, and tolerate missing values. In the e-commerce project a Keras neural network was tried first and was harder to get right: at a 0.7 threshold it predicted every order as "bad". LightGBM reached a higher ROC-AUC with far less tuning, and both models export cleanly to ONNX.

How do you know the reported numbers are real?Approach
Two scripts reload the saved models, reproduce the notebooks' exact splits, and regenerate every figure on the site.

The Titanic script reproduces the notebook's 78.18% accuracy to the digit; the e-commerce script reproduces its 0.8057 ROC-AUC exactly. The site reads these numbers from JSON at load time, so nothing is typed by hand. The reports also state where numbers are optimistic — for example, where tuning and testing shared the same data.

Why do the two projects use different metrics?Approach
Because the class balance and the goal differ.

Titanic is roughly 50/50 and Kaggle scores it on accuracy, so accuracy is a fair target and the threshold maximises it. The e-commerce data is 75/25, where accuracy is misleading and the business goal is to find unhappy customers, so the threshold maximises F1 on the dissatisfied class and ROC-AUC is the headline.

What tools and libraries were used overall?Tools
  • Data: pandas, NumPy, kagglehub (download)
  • Modelling: scikit-learn, LightGBM, XGBoost, Optuna; TensorFlow/Keras in early experiments
  • Deployment: onnxmltools, ONNX Runtime (Python), ONNX Runtime Web (browser)
  • Reporting & site: Jupyter, matplotlib, Chart.js, plain HTML/CSS/JS on GitHub Pages
  • Environment: uv for dependency management
How is the website built and deployed?Tools
Static HTML, CSS and JavaScript with no framework or build step, published by a GitHub Actions workflow on every push.

Charts use Chart.js; the Titanic predictor runs the real ONNX model in the browser with WebAssembly, so no server is involved. The e-commerce dashboard filters a pre-aggregated data cube entirely client-side.

What would you do differently next time?Growth
  • Keep a truly untouched test set and tune on a separate validation set (or nested CV), so the headline number carries no selection optimism.
  • Use time-based splits for the e-commerce data, since real predictions are always about future orders.
  • In Titanic, reorder the cleaning steps so rows are not dropped for gaps in columns that are deleted anyway, and engineer cabin and group features.
  • Report results as a range across several splits rather than a single number.
What was the hardest part?Growth
Not the modelling — the data plumbing and being honest about the numbers.

Joining seven tables without silently duplicating or losing rows took careful row-count checks at every merge. Spotting that seller averages computed on all data leak test information, and accepting the lower score after fixing it, was the most important decision in the e-commerce project.
