Project briefing · 01

Customer satisfaction prediction

Predicting whether a Brazilian e-commerce customer will leave a good review (4–5★), using only information available before they write it — so problem orders can be spotted while there is still time to act.

ROC-AUC 0.8057 Accuracy 84.1% 117,329 rows LightGBM · Optuna · ONNX
01

At a glance

QuestionWill this order get a 4–5★ review?
DatasetOlist Brazilian E-Commerce, 2016–2018 (Kaggle)
Rows modelled117,329 order-item-payment rows
Targetreview_score ≥ 4 → satisfied (75.5%)
Features34, including 5 categorical
ModelLightGBM, 694 trees, tuned with Optuna
Headline0.8057 ROC-AUC · 84.1% accuracy
OutputONNX model, report, dashboard
◆ The one-sentence takeaway. Delivery lateness is the strongest driver of bad reviews: orders that arrive on time are rated 4–5★ 80.2% of the time, late ones only 26.4% — and the model's two most important features both measure delay.

Nine CSV files from a real marketplace, seven of which were joined into one table.

What the data looks like

  • Reviews are extreme: 66,264 five-star and 14,854 one-star rows; mean 4.03, median 5.
  • Almost everyone buys once: customers average 1.03 orders (max 16), so there is no purchase history to lean on.
  • Deliveries arrive early: on average 12.1 days before the promised date.
  • Geographically concentrated: São Paulo state is about 42% of rows.
  • Payments: credit card 73.7%, boleto 19.5%, voucher 5.4%, debit 1.4%.

Quality issues found

  • 610 products had no category → filled with Unknown Category.
  • 2,471 rows have no delivery date — mostly shipped or cancelled orders; 8 were marked "delivered" without one.
  • 15 rows lack an approval timestamp.
  • 8 of 9 primary keys were unique; geolocation repeats, so joining it would have duplicated rows.
03

What was done, step by step

Across four notebooks, in the order they were run.

Load, validate and join the tables

Checked every primary key for uniqueness and every join column for nulls, listed the relationships, then merged step by step while printing row counts: 99,441 → 112,650 (items fan out) → 117,601 (split payments) → 117,329 (orders without reviews drop out).

merge_data.ipynbpandas

Clean and explore

Investigated missing delivery dates, created an on-time flag and approval time, filled missing categories, grouped categories into demand tiers, and profiled prices, freight, instalments, cities and payment types with histograms and summary statistics.

data-analysys.ipynbmatplotlib

Early experiments

On a smaller 11-column table, tried a Keras neural network (bad vs good) and a three-class LightGBM (bad / undecided / good). The network collapsed at a 0.7 threshold, and the three-class model almost never predicted "undecided" (recall 0.02). Both results pointed to a binary target and richer features.

model.ipynbTensorFlow / Keras

Engineer features and iterate on LightGBM

Built delay, freight and time features, then ran five iterations on the same split: with city columns (0.7687), without cities but class-weighted (0.7660), unweighted with interactions (0.7655), seller/category aggregates on all rows (0.7712, leaky), and the same aggregates on training rows only (0.7698).

nl.ipynbLightGBMscikit-learn

Tune with Optuna

Searched nine hyperparameters over 30 trials to maximise ROC-AUC. The best configuration — 694 trees, 127 leaves, depth 10, learning rate 0.063 — lifted ROC-AUC from 0.7698 to 0.8057.

Optuna

Pick a threshold and export

Chose the cut-off that maximises F1 for dissatisfied customers (0.6656). Exported to ONNX and removed the ZipMap node so the model outputs a plain probability array usable from any language.

onnxmltoolsonnx

Report and dashboard

Regenerated every metric with a script, published a technical report, and built an interactive dashboard over 98,353 unique orders.

05

How each conclusion was reached

Every claim, the evidence behind it, and the decision it led to.

C1

Lateness is the main driver of bad reviews

EvidenceSatisfaction drops from 76.6% to 37.5% between "just early" and "just late". The top two features by gain both measure delay (24% combined).
How it was checkedConfirmed three independent ways: a grouped table in exploration, model feature importance, and again in the dashboard at order level (82.7% vs 26.7%).
DecisionDelay features became the core of the feature set. Business action: accurate delivery promises matter more than price.
C2

A binary target works better than three classes

EvidenceThe three-class LightGBM reached 79.7% accuracy but recall of just 0.02 on 3★ "undecided" reviews — only 8.4% of data and hard to separate.
How it was checkedClass weighting raised that recall to 0.15 but dropped accuracy to 72.8%, so the class was genuinely hard, not just under-weighted.
DecisionBinary target: 4–5★ satisfied, 1–3★ not. A 3★ review on this marketplace reads as a complaint.
C3

Tree boosting beats the neural network here

EvidenceThe Keras network predicted every order as bad at threshold 0.7 (16% accuracy). Retuned to 0.39 it managed 0.41 precision on bad reviews.
How it was checkedLightGBM on richer features reached 0.77 ROC-AUC before tuning and 0.8057 after, with native categorical and missing-value handling.
DecisionLightGBM for the final model — stronger, faster, easier to interpret and to export.
C4

City columns should be dropped

EvidenceWith cities included, customer_city and seller_city were the two most-used features, far ahead of anything about delivery.
How it was checkedThousands of city values let trees memorise locations. Removing them shifted importance to category, price and delay — features that describe why customers are unhappy.
DecisionDropped cities; kept state-level location, which generalises.
C5

Seller averages must be computed on training rows only

EvidenceComputed on all rows, seller and category averages include each test order's own delay — test information leaking into features (0.7712).
How it was checkedRebuilt with a split-first pipeline: aggregates learned from training rows, unknown sellers filled with training-set averages. Score: 0.7698.
DecisionKept the leakage-free version despite the lower number. An honest score beats a flattering one.
C6

The threshold should be 0.6656, not 0.5

EvidenceWith 75% satisfied rows, a 0.5 cut calls almost everyone satisfied and misses unhappy customers — the ones that matter.
How it was checkedSwept every threshold with a precision–recall curve and picked the one maximising F1 on the dissatisfied class.
Decision0.6656 — the model flags an order as at-risk unless it is fairly confident the customer is happy.
C7

0.8057 is a good estimate, but an optimistic one

EvidenceOptuna scored its 30 trials on the same test rows that report 0.8057, so the winner was partly chosen for suiting that sample.
How it was checkedReproduced 0.8057 exactly with a script. Removing 15 rows before splitting moved it to 0.7936, showing how much a single split varies.
DecisionReport 0.8057 with the caveat, and treat 0.79–0.81 as the realistic range. Next time: a separate tuning set.

07

Questions & answers

The questions a reviewer is most likely to ask, with short answers first.

What problem does this project solve?Problem
It predicts which orders are likely to get a bad review before the customer writes it.

Reviews arrive after delivery, when it is too late to fix anything. A model that flags risky orders early lets a marketplace contact the customer, prioritise a late shipment, or review a problem seller.

How did you define "satisfied", and why that cut-off?Problem
4 or 5 stars is satisfied; 1–3 stars is not.

Three-star reviews are only 8.4% of rows and a three-class model could not predict them (recall 0.02). On this marketplace 3★ usually reflects a complaint, so grouping it with 1–2★ gives the business the signal it needs. The result is 75.5% satisfied, 24.5% not.

When in the order's life would this model be used?Problem
After delivery information is known, but before the review is written.

Several key features — delivery delay, actual delivery days — are only known once the order arrives. So this is an early-warning model at delivery time. A version that scores at purchase time would need to rely on estimated delivery and seller history instead.

How did you join the tables without losing or duplicating data?Data
By validating keys first and checking the row count after every merge.

Every primary key was tested for uniqueness and every join column for nulls. Each merge was run separately with its row count printed, and each change was explained: items and split payments legitimately add rows (99,441 → 117,601), and orders without reviews drop out (−272). The geolocation table was left out because its key repeats and would have multiplied rows.

Why are there more rows (117,329) than orders (99,441)?Data
An order with several items or several payments appears once per combination.

That means multi-item orders carry more weight in training. It is a known limitation; the dashboard fixes it by aggregating to one row per order (98,353 orders), and a future model version should do the same.

How did you handle missing values?Data
  • Product category (610 products): filled with Unknown Category, so these rows still count.
  • Delivery dates (2,471 rows): investigated first — most belong to orders that were shipped or cancelled, not delivered. LightGBM handles the resulting missing delay values natively.
  • Product dimensions: left missing; LightGBM learns which way to send missing values at each split.
Which features did you engineer, and why?Data
  • Delay: delivery_delay_days (actual − promised), is_delayed, delay_severity (delay relative to the promised window), actual_delivery_days, estimated_delivery_days.
  • Cost: freight_ratio (shipping as a share of spend), freight_per_gram, price_per_volume.
  • Context: same_state, purchase hour, weekday and month.
  • Track record: seller average delay and order count, category average delay and freight — computed on training rows only.

Each captures a plausible reason for disappointment: late arrival, expensive shipping, or an unreliable seller.

Which columns did you deliberately exclude?Data
Anything written after the outcome, raw IDs, and very high-cardinality text.

Review text, title and timestamps describe the review itself — using them would be leakage. IDs let trees memorise specific orders. Customer and seller cities were removed after they dominated feature importance (see the city question below).

Why LightGBM?Model
  • Handles the five categorical columns natively — no need to one-hot 70+ product categories.
  • No feature scaling needed for prices in the thousands next to 0/1 flags.
  • Handles missing values without imputation.
  • Outperformed the Keras network that was tried first, and exports to ONNX.
Why did you remove the city columns?Model
The model was memorising cities instead of learning reasons.

With cities included, customer_city (3,089 splits) and seller_city (1,767) were the top features — far ahead of delivery delay (340). Thousands of city values let trees carve out tiny local groups that will not generalise. After removal, importance shifted to category, price and delay, and ROC-AUC was essentially unchanged (0.7687 → 0.7660 with weighting).

Why not use class weights for the imbalance?Model
It improved recall but hurt ranking, and a tuned threshold achieves the same trade-off.

With scale_pos_weight, dissatisfied recall rose from 0.38 to 0.59, but ROC-AUC fell and the probabilities became less meaningful. Training unweighted and moving the decision threshold keeps calibrated probabilities while still catching more unhappy customers.

What leakage did you find, and how did you fix it?Model
Seller and category averages were first computed on all rows, including test rows.

A test order's own delay was then baked into its seller's "average delay" feature. The fix was to split first, compute the averages on training rows only, and fill unseen sellers with training-set means. ROC-AUC went from 0.7712 to 0.7698 — slightly lower, and the version that was kept.

How did Optuna tuning work, and what did it find?Model
30 trials of Bayesian search over nine parameters, maximising ROC-AUC.

Optuna's TPE sampler uses results from earlier trials to choose promising settings. It searched trees (200–800), learning rate (0.01–0.1), leaves (15–127), depth (3–10), minimum child samples, row and column subsampling, and L1/L2 regularisation. The winner used 694 trees, 127 leaves and depth 10, raising ROC-AUC from 0.7698 to 0.8057.

Why ROC-AUC as the main metric instead of accuracy?Evaluation
Because predicting "satisfied" for everyone already scores 75.5% accuracy.

ROC-AUC measures how well the model ranks unhappy customers above happy ones, regardless of threshold and unaffected by imbalance. Accuracy (84.1%) is still reported, alongside per-class precision and recall. ROC-AUC explained →

How did you choose the 0.6656 threshold?Evaluation
It maximises F1 for the dissatisfied class.

Using precision_recall_curve on the dissatisfied class, F1 was computed for every threshold and the best one kept. At 0.6656 the model catches 55.4% of unhappy customers, and 73.2% of its "unhappy" flags are correct.

How would you explain these results to a non-technical manager?Evaluation

"If we contacted every order the model flags, about 7 in 10 would be genuinely unhappy customers, and we would reach just over half of all unhappy customers before they post a review. The biggest lever is delivery: late orders are three times less likely to get a good review."

How confident are you in 0.8057?Evaluation
Confident it is reproducible; aware it is somewhat optimistic.

A script reproduces it exactly. But Optuna chose parameters by scoring on the same test rows, and removing just 15 rows before splitting changes the score to 0.7936. A realistic expectation is roughly 0.79–0.81. A separate tuning set or repeated splits would narrow that down.

Where does the model make mistakes?Evaluation
Mostly unhappy customers whose orders looked fine logistically.

2,569 dissatisfied rows were predicted satisfied. Many are likely complaints about the product itself — quality, wrong item, description mismatch — which none of the 34 features can see. That caps recall on the dissatisfied class regardless of the algorithm.

Why export to ONNX, and what is ZipMap?Deployment
ONNX runs the model without Python; ZipMap was removed to keep outputs simple.

The ONNX file can be served from C#, Java, JavaScript or a mobile app. By default the converter adds a ZipMap step that wraps probabilities in a list of dictionaries, which many runtimes handle poorly. Removing it makes the output a plain [N, 2] float array.

What would it take to put this in production?Deployment
  • Package the category encoding with the model — ONNX expects the same category codes used in training.
  • Recompute seller and category averages on a schedule from recent history.
  • Monitor the prediction distribution and delivery patterns for drift.
  • Retrain periodically and validate on the most recent months, not a random split.
What are the main limitations?Limits
  • Random, not time-based split: 2018 orders can help predict 2017 ones.
  • Row inflation: multi-item orders count several times.
  • No product-quality signal: limits how many unhappy customers can be caught.
  • New sellers fall back to global averages.
  • Tuning and testing shared a split, so the headline is slightly optimistic.
What would you improve next?Limits
  • Add customer–seller distance from the unused geolocation table.
  • Model at one row per order to remove duplication.
  • Use a time-based validation with a separate tuning period.
  • Build seller quality scores from their past reviews — legitimate because it uses earlier orders only.

No questions match that search.
