Project briefing · 02

Spaceship Titanic

A controlled comparison of tree-based classifiers predicting whether a passenger was transported to another dimension, followed by tuning, threshold selection and a browser deployment of the winning model.

ROC-AUC 0.8687 Accuracy 78.18% 8,693 labelled rows LightGBM · ONNX

The data

One flat competition dataset with mixed categorical, numeric and composite fields.

What was used

  • Numeric: age and five onboard spending columns.
  • Categorical: home planet, cryosleep, destination and VIP.
  • Encoding: one-hot encoding produced the 16-column model matrix.

What was excluded

  • Cabin: shared group information could leak across a random split.
  • Name: nearly unique, so it would encourage memorisation.
  • PassengerId: retained only for labelling submissions.
03

What was done, step by step

From cleaning and benchmarking to a reproducible browser model.

Clean and inspect

Loaded the train and test files, filled missing categoricals with an explicit Unknown level, median-filled test numerics, and removed remaining incomplete training rows. This left 7,265 labelled rows.

data_cleaner.ipynbpandas

Encode the features

Dropped Cabin and Name for leakage and memorisation reasons, then one-hot encoded the remaining categoricals. The model receives 16 numeric columns in a fixed order.

pandasscikit-learn

Benchmark nine models

Compared five tree learners and four voting ensembles on the same stratified 80/20 split. Gradient boosting led the untuned field at 78.05%; the ensembles did not beat it.

train_ensemble.ipynbscikit-learnLightGBM

Tune LightGBM

RandomizedSearchCV tested 30 candidates from a nine-parameter space with five-fold cross-validation. The selected model uses 100 trees, 31 leaves, a 0.05 learning rate and L2 regularisation.

RandomizedSearchCV30 draws

Choose a threshold

Swept the validation probabilities instead of assuming 0.5. Because the target is balanced, accuracy is a reasonable objective; the best cut-off was 0.42.

threshold sweepROC-AUC

Export and deploy

Exported the final model to ONNX with a fixed float32 input contract, then connected it to an ONNX Runtime Web predictor so a passenger can be scored in the browser without Python.

onnxmltoolsONNX Runtime Web

05

How each conclusion was reached

Evidence, interpretation and the decision that followed.

C1

No voting ensemble beat its best member

EvidenceFour voting schemes scored 77.29%–77.77%, while gradient boosting alone reached 78.05%.
How it was checkedEvery model saw the same features and the same stratified validation rows.
DecisionCarry LightGBM forward for tuning and deployment; do not claim ensembles helped.
C2

LightGBM was chosen for tuning headroom, not a benchmark win

EvidenceThe top six untuned models sit within 0.8 percentage points, inside the noise of one split.
How it was checkedRandomizedSearchCV gave LightGBM a reproducible search path and a model that exports cleanly.
DecisionUse the tuned model while treating small benchmark differences cautiously.
C3

Explicit missingness was preferable to inaccurate imputation

EvidenceA model-based imputer reached only 72.3% accuracy for missing categoricals.
How it was checkedUnknown indicators let the classifier use missingness directly; the training and test handling was documented separately.
DecisionKeep an explicit Unknown category, while fixing the later row-drop issue in the next iteration.
C4

The threshold should be 0.42, not 0.5

EvidenceAccuracy rises from 77.84% at the default threshold to 78.18% at 0.42.
How it was checkedA sweep evaluated the validation probabilities across possible cut-offs.
DecisionUse 0.42 in the report and the browser predictor, while recording that selection and evaluation share data.
C5

The model ranks better than its labels suggest

EvidenceROC-AUC is 0.8687 while thresholded accuracy is 78.18%.
How it was checkedAUC evaluates ranking across all thresholds; accuracy evaluates one operating point.
DecisionReport both: AUC describes ranking quality, and accuracy describes the chosen action rule.

07

Questions & answers

The questions a reviewer is most likely to ask.

Why were 1,428 training rows dropped?Data
The original cleaning sequence ran dropna() before unused columns were removed.

That means some rows were discarded for gaps in Cabin or Name, even though those fields were never model features. The next version should drop those columns first and median-fill numeric gaps consistently.

Why not use the Cabin column?Data
Raw cabin values are high-cardinality and shared across passengers.

A random split could place passengers from the same cabin on both sides, allowing the model to learn group identity rather than general patterns. Splitting Cabin into deck, number and side is a strong next experiment, but it needs group-aware validation.

Why did the ensembles not help?Model
The component models made correlated errors on the same passengers.

Hard and soft voting landed between 77.29% and 77.77%, below gradient boosting's 78.05%. Voting helps when members fail on different rows; these models did not provide enough independent signal.

Why choose LightGBM?Model
It was competitive in the benchmark, improved under search and has a practical export path.

It handles tabular interactions well, needs no scaling, and the final model is small enough to run client-side through ONNX Runtime Web.

Why report ROC-AUC as well as accuracy?Evaluation
They answer different questions.

Accuracy describes one threshold. ROC-AUC describes how consistently the model ranks transported passengers above non-transported passengers across all thresholds. The balanced target makes accuracy useful here, but it does not replace ranking quality.

How was 0.42 selected?Evaluation
A validation sweep found the accuracy-maximising cut-off.

At 0.42 the model reaches 78.18%, compared with 77.84% at 0.50. The same split is used for selection and reporting, so this improvement should be treated as slightly optimistic.

What would you improve next?Limits
  • Drop unused columns before removing incomplete rows.
  • Engineer Cabin, group-size and companion features.
  • Compare models across repeated or nested stratified splits.
  • Keep a separate validation set for threshold selection.
